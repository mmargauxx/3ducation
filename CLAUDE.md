# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`3ducation` is a custom **WooCommerce block theme (Full Site Editing)** for [3ducation.be](https://3ducation.be), a Belgian 3D-printing shop (printers, filament, resin, accessories, workshops). It is **theme source only** — no products, pages, or content live here; those are entered on the live site. There is **no build step**: `theme.json`, HTML block templates, and PHP block patterns are shipped as-is. UI copy is Dutch (nl_NL / EUR / BE).

The repo also carries a few things that are **not part of the theme zip**: four must-use plugins deployed separately into `wp-content/mu-plugins/` — `mu-plugins/3ducation-legacy-redirects.php` (the old Duda-shop 301s) and `mu-plugins/3ducation-pos-cadeaubon.php` (reports the PW gift-card product as `variable` to WooCommerce POS requests only, so the till offers the amount variations and sends a `variation_id`; it also blocks a POS write-back from flipping the product type) and `mu-plugins/3ducation-cadeaubon-vervaldatum.php` (free PW Gift Cards cannot set expiry dates at all; this hooks `pwgc_activity_create` to give every new card 2 years from purchase, appends "Geldig tot …" to the gift-card e-mail, and carries a one-off `?3du_verval_bonnen=test|doen` backfill for new-shop cards; migrated cards are backfilled by a Drive-only script because it embeds card codes) and `mu-plugins/3ducation-bestelstatussen.php` (two extra order statuses: `wc-afhaalklaar` "Klaar voor afhaling" for pickup orders only — detected on the shipping line: `pickup_location`/`local_pickup` or a method name containing afhal/ophal/pickup; list quick-action + bulk action + status dropdown restricted to pickup orders, a guard reverts the status on non-pickup orders; customer e-mail `customer_afhaalklaar` with the shop address/opening hours from the theme footer option, editable under WooCommerce → E-mails; and `wc-verzonden` "Verzonden", admin-only bookkeeping for shipped orders: quick-action on non-pickup processing orders + bulk action, no e-mail, no guard) — plus `GO-LIVE.md` (the server-side checklist), and gitignored local tooling (`_import/` CSV/option importers, `.claude/`, `.agents/`, `*.zip`, `*.pdf`, `overdracht.html`). `.gitattributes` marks the non-theme files `export-ignore` so `git archive` produces a clean theme zip.

## Local development

Requires Docker (or OrbStack) and **Node 22 LTS** — newer Node breaks `wp-env`'s native install step, and the WordPress container silently fails to recreate (site goes down) on Node 26.

```bash
export PATH="$HOME/.nvm/versions/node/v22.23.1/bin:$PATH"   # nvm use 22 does NOT stick in non-interactive shells
npm install
./node_modules/.bin/wp-env start      # or: npm start
```

- Site: http://localhost:8888 · Admin: http://localhost:8888/wp-admin (`admin` / `password`)
- Stop: `npm stop` · Reset DB: `npm run clean` · Tear down: `npm run destroy`
- WP-CLI inside the container: `./node_modules/.bin/wp-env run cli wp <command>`
- **Avoid restarting wp-env** unless `.wp-env.json` changed. Options and theme-file edits need no restart; the MySQL volume (products, options) survives restarts.

`.wp-env.json` provisions WooCommerce + WordPress Importer, PHP 8.2, and `WP_DEBUG`/`SCRIPT_DEBUG` on. The gitignored `.wp-env.override.json` pins the WordPress core version (currently the 7.0 branch) — check it before assuming "latest".

There are no tests and no linter; verification is visual (screenshots) plus `php -l` on edited PHP.

### Gotchas (verified, but re-check against current code)

- **Pattern cache:** after adding OR editing any `patterns/*.php`, `wp cache flush` alone is NOT enough — the block-pattern list is cached separately. Run `./node_modules/.bin/wp-env run cli wp eval 'wp_clean_themes_cache(); wp_cache_flush();'` or the pattern renders empty/stale. Template HTML edits (`templates/*.html`) are read from disk — no cache clear needed. **This bites during local editing only**, where the theme version stays put: since WP 6.4 the cache is keyed on the theme's `Version:` header (`WP_Theme::get_pattern_cache()`), so a released version bump invalidates it by itself — see `GO-LIVE.md`. To stop it biting locally at all, add `"WP_DEVELOPMENT_MODE": "theme"` to `config` in `.wp-env.json`; core then skips the pattern cache entirely.
- **Coming-soon mode:** WooCommerce ships with `woocommerce_coming_soon=yes`, so `/shop` shows a placeholder. `wp option update woocommerce_coming_soon no` to see the real storefront (a DB setting, not in the theme).
- **CSS cache:** `custom.css` is enqueued with a fixed `?ver` (`THREEDUCATION_VERSION`), so edits don't bust returning browsers' cache — hard-refresh. Headless-Chrome screenshots are always fresh and can disagree with the browser.
- **Screenshots:** headless Chrome works — `"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless --disable-gpu --hide-scrollbars --window-size=W,H --virtual-time-budget=4000 --screenshot=out.png URL` (the virtual-time budget lets CSS load animations settle).
- **Site Editor overrides:** saving a template or template part in the Site Editor writes a copy to the DB that permanently shadows the theme file — theme updates to that template stop showing until the DB copy is deleted (Site Editor → "Clear customizations"). This is why the footer texts have an admin screen instead of relying on the editor. If a template change does not show up on local or live, check for a DB override first.
- **Site Editor in Chrome:** works normally (confirmed 2026-09-01). The `Block validation failed for woocommerce/product-filter-*` / `product-image` console spam is unrelated WooCommerce noise — ignore it.

## Architecture

Styling is **data-driven, layered by intent** — put a change at the lowest layer that can express it:

1. **`theme.json` (v3)** — the design system and single source of truth for tokens: the tricolor brand palette (magenta/cyan/amber), a light-neutral ramp (`base`/`surface`/`ink`/`ink-soft`/`muted`/`border`/`base-soft`) and a **dark sub-palette for dark sections** (footer, intake forms, dark panels): `surface-dark`, `ink-line` (dividers/borders on dark), `mist` (soft body text on dark), `mist-soft` (placeholder text on dark). Plus the multi-stop `cube` gradient, self-hosted Space Grotesk `display` font, and fluid type/spacing scales (spacing `20`→`80`, with `45` = 2rem for card padding). Most visual changes belong here, referenced as `var:preset|color|magenta`, `var:preset|spacing|60`, etc. `defaultPalette`/`defaultGradients`/`defaultFontSizes`/`defaultSpacingSizes` are all disabled — only the presets defined here exist. **Design source is fully tokenized** — `custom.css`, templates, and patterns carry no raw design hex (only functional `#000` luminance masks, the `cube` gradient fallback stops, and hex inside SVG `data:` URIs remain). `customTemplates` registers the six pillar/contact page templates plus `page-no-title`.
2. **`assets/custom.css`** — ONLY the supplementary rules `theme.json` can't express: the category bento grid, the kinetic partner marquee, hover micro-physics, the site-notice bar, form styling, the category-intro read-more. Enqueued in `functions.php` and also loaded as an editor stylesheet. Don't add here what a `theme.json` token or block attribute can do. WooCommerce/core CSS often needs `!important` to override — that is expected, not a smell.
3. **`templates/*.html` + `parts/*.html`** — block-markup templates (`front-page`, `archive-product`, `single-product`, `product-search-results`, `page-cart`, `page-checkout`, `page-<pillar>`, `index`, `search`, `404`, …) and the `header`/`footer` parts. **`parts/footer.html` is a one-line reference to the `3ducation/footer` pattern** so the footer can render client-editable text; the markup lives in `patterns/footer.php`. Templates compose patterns and WooCommerce blocks; they carry inline block attributes, not custom CSS.
4. **`patterns/*.php`** — reusable block-markup sections registered to the `3ducation` pattern category. Each file's PHP docblock (`Title:`, `Slug: 3ducation/<name>`, `Categories:`) is the registration; the body is block HTML. Patterns are referenced from templates via `<!-- wp:pattern {"slug":"3ducation/hero"} /-->`. Pattern PHP runs **per request**, so patterns render live data: `product-spotlights` (the shop category chips, despite the file title) queries top categories, `product-banner` renders the admin-selected spotlight products, `category-intro` renders the category thumbnail + markdown description, `shop-filters` looks up product-attribute IDs at render time (they differ per environment — never hardcode them), `product-trust` reads the trust-badge option, `footer` reads the footer option. **Three patterns are registered but referenced by no template** (`featured-products`, `product-categories`, `workshops-cta`) — they are inserter-only; check before assuming a pattern edit is visible somewhere.

**Never hardcode shop URLs in patterns.** WooCommerce's category base is a translatable string (`product-category` becomes `product-categorie` under nl_NL) and the cart/checkout/account pages can be moved by the admin. Use `threeducation_product_cat_url( $slug, $fallback )` and `threeducation_wc_page_url( 'cart'|'checkout'|'myaccount'|'shop' )` from `functions.php`; both fall back to something that never renders an empty href. Plain `/shop` links in templates and the pillar page links (`/workshops`, `/oplossingen`, …) are fine — those are theme-owned slugs.

### `functions.php`

The only substantive PHP (~2,500 lines, one file on purpose). It is organised in commented sections; the ones a future change is likely to touch:

- **Theme wiring:** supports, WooCommerce declaration + product-gallery features, asset enqueue (callback is misspelled `threducation_enqueue_assets` — keep it), pattern-category registration (label `3DUCATION`, slug `3ducation`), a `gettext_woocommerce` gap-filler for strings the nl_NL pack misses, and the product-search placeholder.
- **Client-editable settings screens** (all under wp-admin **Settings**, each stored in one option, each with a `_defaults()` + a merge/resolve function so an empty field falls back to the default rather than erroring): *Site melding* (dismissible notice bar with date window; content-hash `id` so an edited message re-shows to visitors who dismissed the old one; `assets/notice.js` + `localStorage`), *Site pop-up* (centred modal with title, body, optional button and date window; same id/dismissal model under the `3ducation:popup-dismissed` key; a native `<dialog>` printed closed at `wp_footer` and opened by `assets/popup.js`, so Escape, focus trap and backdrop are browser-native; once closed, a fixed bottom-left pill reopens it so the message stays rereadable; the body textarea becomes paragraphs via `threeducation_popup_paragraphs()`), *Uitgelichte producten* (up to three shop spotlights, falls back to newest three), *Vertrouwensbadges* (the three badges next to Add-to-Cart), *Boekingslinks* (Cal.com URLs, see below), *Footer* (opening hours, address, phone/e-mail, brand row; multi-line fields become `<br>` via `threeducation_footer_multiline()`).
- **Per-category spotlights** — each `product_cat` term can pick three spotlight products (term meta, edited on the category screen); resolution cascades term choice → WooCommerce "featured" star → global spotlights, all through the same resolver so visibility windows apply.
- **Category descriptions as markdown** — rendered through the vendored `inc/Parsedown.php` (`threeducation_render_markdown()`), used by `category-intro`; the admin category list shows a truncated description column.
- **Product visibility window** — `_visible_from` / `_visible_until` product meta (inclusive, site-local Y-m-d). Out-of-window products are filtered from every front-end query via `pre_get_posts`, 404 on their single page, are non-purchasable, and are dropped from related products; the hidden-ID set is cached and flushed on product save. Admin gets a "Zichtbaarheid" column and a submit-box status. Used for workshop sessions that should disappear after their date.
- **Pre-order plugin integration** (Pre-Orders for WooCommerce, XootiX) — moves the "Available on" flag onto the product image to match the sale badge; the plugin's own filter is spelled `preorder_avaiable_date_text`.
- **Per-pillar SEO** — hand-written `<title>` + meta description/keywords keyed on page slug in `threeducation_pillar_seo()`. A real SEO plugin, if added, takes over.
- **Webshop sorting** — replaces WooCommerce's order-by list (A→Z default, Z→A, rating, price, release date) and implements the title orderings WooCommerce lacks. The shop's Product Collection block has `inherit:true`, so the catalog-sorting dropdown drives it.
- **Category filter indentation** — post-processes the rendered `product-filter-taxonomy` block HTML to indent subcategories (both the visible text and the `data-wp-context`); the long comment above it explains why no cleaner hook exists.
- **BTW-nummer (VAT)** — custom field on customers (`billing_vat` user meta) and orders (`_billing_vat`), normalised to uppercase without spaces/dots on every write; searchable in the order-screen customer lookup.
- **Cal.com booking links** — `threeducation_calcom_url( $event )` resolves admin value → hardcoded default → `threeducation_calcom_url` filter. `threeducation_calcom_popup_path()` decides per link whether the button gets the popup embed (`assets/cal-embed.js`) or a plain new-tab link: only a `cal.com/<user>/<event-slug>` path gets the popup. The workshop uses Cal.com's fixed-date **Events** pages, so it is new-tab by design and its URL changes per session.
- **Intake forms** — `contact-form`, `service-intake`, `workshops-intake` POST to `admin-post.php` (`threeducation_handle_intake`); `threeducation_intake_config()` is the field map, `_hidden_fields()`/`_notice()` render nonce+honeypot and the result banner. Validates and `wp_mail()`s; recipient per form via the `threeducation_intake_recipient` filter (live: FluentSMTP is configured). The service form attaches images/videos. No form plugin — the hand-styled markup stays. (The "layout placeholder" NOTE in the three pattern docblocks is stale.)
- **Legacy redirects** used to live here and were moved to the mu-plugin. Do not put them back: the mu-plugin loads first and PHP fatals on the duplicate function declarations.

### Content flow

The homepage (`front-page.html`) is a brochure — hero → **pillars** (three-way split) → **audience-split** (B2B/B2C: Voor Scholen vs Voor Thuis, two-up, color-coded per pillar — scholen = cyan (→educatie), thuis = magenta (→webshop)) → partners → webshop-CTA. The site is organised around **three pillars**, each a slug-mapped page (`page-<slug>.html` + patterns, registered in `theme.json` `customTemplates`):
- **`/oplossingen`** ("3D-printen" in the nav) — Webshop & oplossingen: schools (→ `/educatieve-pakketten`) + home users (→ `/shop`).
- **`/workshops`** — Leren & opleidingen: workshop detail, birthday parties, schools section, audiences, intake form.
- **`/service`** — Service & montage: repair intro/checklist + a repair intake form.

Plus **`/educatieve-pakketten`** (deep package detail), **`/over-ons`** (About: team, "Uit de praktijk" gallery, promises, dual CTA) and **`/contact`** (hero, contact info, contact form). The header nav is 3D-printen(=/oplossingen) / Workshops & Educatie / Service & Montage / Over ons / Contact (Webshop is a separate button). **Educatie is anchored on the Workshops pillar** (the "Workshops & Educatie" label + the `workshops-scholen` section); the Oplossingen pillar's "Voor scholen" block is a short teaser that cross-links there. The Webshop (`/shop`, `archive-product.html`) leads with the category intro (on category archives), the three-product spotlight strip + category chips, then the filter sidebar and the sortable product grid. Everything downstream (products, cart, checkout) is standard WooCommerce blocks styled through `theme.json`. **Pillar pages stay FSE templates + patterns**, not editable Page posts: the Page in wp-admin is an empty shell whose only job is to exist so the slug resolves (a missing Page 404s the nav link).

## Conventions

- **Naming:** PHP prefix is `threeducation_`. The **text domain and pattern-category slug stay `3ducation`** (lowercase); do not rename them. Version constant `THREEDUCATION_VERSION` lives in both `functions.php` and `style.css` (check both for the current number) — **bump both together on every change that ships**; it is the asset cache-buster **and** the key that invalidates WordPress's block-pattern cache on deploy. Commit messages are Dutch and carry the version, e.g. `Maak de footerteksten bewerkbaar voor de klant (v0.18.22)`.
- **Brand:** magenta is the primary/action color (primary buttons stay magenta site-wide); the `cube` gradient and per-section color-coding (magenta/cyan/amber) are the visual signature. **Section accents map to pillars:** magenta = 3D-print oplossingen & webshop, cyan = workshops & educatie, amber = service & montage — and the B2B/B2C split follows suit (scholen = cyan, thuis = magenta). Decorative tricolor sets that enumerate items rather than pillars (package tiers, workshop steps, empty-state/404) keep all three accents. **Exceptions:** the shop's category chips (`product-spotlights.php`) and the "Uitgelicht" spotlight strip (`product-banner.php`) are amber-only; the educatie/workshops cards and steps are cyan-only. Keep new UI within the existing palette — use a `theme.json` token (add one there if none fits). In block markup, reference a preset in an inline style as `var:preset|color|<slug>` so the `has-*` class list stays intact and the block still validates. **The brand name is stylised `3DUCATION` (all-caps) in all user-facing copy**, but identifiers stay lowercase `3ducation` (text domain, pattern slugs, CSS classes, PHP prefixes, `3ducation:notice-dismissed` localStorage key, `info@3ducation.be`).
- **Localization:** all user-facing strings are Dutch and wrapped in `__()`/`esc_html__()` with the `3ducation` text domain. Code comments in newer sections are Dutch too; either language is fine.
- **Responsive:** the 782–1023px tablet band is the weak spot; check it when touching layout. `:has()` selectors cannot nest. Cart/checkout strings come from WooCommerce's JS i18n, not the theme.

## Deployment

Live site runs on **EasyHost Managed WordPress**. Full procedure in `GO-LIVE.md`; the short version:

```bash
git archive --format=zip --prefix=3ducation/ -o 3ducation-<versie>.zip HEAD
```

`--prefix=3ducation/` is mandatory — without it WordPress creates a second theme folder named after the zip and Site Editor customisations detach. Upload via Appearance → Themes (replace) or SFTP into `wp-content/themes/3ducation/`. The version bump is the cache flush; no WP-CLI needed on the host. The mu-plugin is uploaded separately to `wp-content/mu-plugins/`. Content, WooCommerce settings and plugins do not travel with the theme — never copy the local wp-env database to the server.
